# API Test Planning

Turn an API's OpenAPI contract into a test plan and test cases that **testers, developers and product owners can all read**, before any API test is automated. The contract is the source; live calls only fill gaps the contract leaves.

## Critical

- **Contract first.** Plan from the contract via `api-context/<site>/INVENTORY.md`. Don't plan from what the API happens to return today. A live response may fill a *gap* (e.g. an undocumented error body) and is labelled **Seen in live response**.
- **Plain English.** Steps, request descriptions and expected results are sentences. The **only** technical items allowed are in two fields: **Endpoint** (`METHOD /path`) and **Expected response** (status code plus its standard name, e.g. "**401 Unauthorized**"). No JSON, code, headers syntax, field-type jargon or tool names anywhere else. Describe data in words: "without an access key", "with the email missing", "a product ID that doesn't exist".
- **Every documented status code of an in-scope operation gets at least one case**, or is listed in the plan as deliberately not covered, with a reason.
- **Label every expected result:** **Documented in contract**, **Seen in live response**, or **Needs confirming** (the contract is silent and it hasn't been observed). Never present a guess as documented.
- **Contract problems are findings, not fixes.** A missing auth requirement, an undocumented error body, or a status the API doesn't honour goes in the plan's *Contract findings*. The case states what *should* happen.
- **Mark cases that create or change data** ("Changes data: yes, clean up by …"). On a shared demo, every such case needs a cleanup step.
- **Readable file names**, numbered in a sensible order: `01-users-and-login.md`, `04-invoices.md`.

## Layout

```
api-context/<site>/
  openapi.json                 contract snapshot (as fetched; diff it to spot contract changes)
  INVENTORY.md                 generated: one table per resource — method, path, auth, params, required body fields, documented responses
test-plans/<site>/api/
  test-plan.md                 the API plan (template below)
  test-cases/
    01-<resource>.md           one file per contract tag / resource group in scope
    02-<resource>.md
```

`<site>` matches `ui-context/<site>/`, `test-plans/<site>/` and the fixture name. Generate the context with:

```bash
npm run api:inventory -- "<contract URL or file>" --site <site> [--tags User,Invoice]
```

Re-run when the contract may have changed. `git diff api-context/<site>/openapi.json` shows what changed. Reuse the existing inventory otherwise (same idea as `ui-context`: build context once, plan many times).

## Scope first

Large contracts (Toolshop: 88 operations) are planned in slices. Decide scope **before** writing:
1. Resources the UI test plan relies on (its backend checks and critical flows) → in scope first.
2. Resources that change data or handle money/auth → next.
3. Read-only reference data (brands, categories) → later or lower priority.
If scope isn't stated, propose it in the Phase 4 proposal and ask (`ai-native-workflow`).

## Scenario checklist (per operation in scope)

Derive cases from the inventory row. Skip a line only if it truly doesn't apply.

| # | Scenario | When it applies | Usual priority |
|---|---|---|---|
| 1 | **Successful call**: valid request, expected success code, response has the documented shape | always | High (critical resources) / Medium |
| 2 | **No access key** → 401 | Auth = yes | High |
| 3 | **Expired or invalid access key** → 401 | Auth = yes | Medium |
| 4 | **Not allowed for this role** → 403 | 403 documented, or role-based resource | Medium |
| 5 | **Empty request body** → 400/422 | has a request body | Medium |
| 6 | **Each required field missing**: one data-driven case listing every required field as a variation | has required body fields | Medium |
| 7 | **Wrong kind of value per field** (text where a number is expected, etc.): data-driven | has a request body | Medium |
| 8 | **Business rules** the contract or exploration reveals (e.g. state must belong to country) | known rule | High/Medium |
| 9 | **Something that doesn't exist** (unknown ID) → 404 | path parameter or 404 documented | Medium |
| 10 | **Badly formed IDs** in the path (text, symbols, an injection attempt): data-driven | path parameter | Low |
| 11 | **Wrong method** → 405 | 405 documented | Low |
| 12 | **Conflict** (duplicate, in use) → 409 | 409 documented | Medium |
| 13 | **Any other documented status** not covered above | always | by impact |

**Data-driven cases** list their variations in a small table instead of being split into many cases. The plan counts the case once and reports the number of variations.

## Writing rules

| Write | Not |
|---|---|
| "Send a login request with a registered customer's email and a wrong password." | `POST {"email":"…","password":"x"}` |
| "Send the request without an access key." | "omit the `Authorization: Bearer` header" |
| "The service refuses it (**401 Unauthorized**) and returns no access key." | "status 401, body.error === 'Unauthorized'" |
| "The response has the documented product details (name, price, category …)." | "matches `ProductResponse` schema" |
| "Each of these left out, one at a time: street, city, state …" | "`billing_street` omitted → 422" (use the plain field meaning, then the field name in brackets only if testers need it: "street (billing_street)") |

## Labels

| Label | Values |
|---|---|
| Priority | **High** · **Medium** · **Low** |
| Type | Functional · Authentication · Authorisation · Validation · Business rule · Not found · Robustness · Contract |
| Basis | **Documented in contract** · **Seen in live response** · **Needs confirming** |
| Changes data | **No** · **Yes — clean up by …** |
| ID | `API-<RES>-<NN>` (e.g. `API-USR-03`, `API-INV-07`). RES is a short code per resource file; never reuse IDs |

## Test-case template

```md
### API-USR-03 — Login is refused with a wrong password

- **Priority:** High
- **Type:** Authentication
- **Endpoint:** `POST /users/login`
- **Before you start:** Know a registered demo customer's email address.
- **Request:** Send a login request with that email address and a wrong password.
- **Expected response:** **401 Unauthorized**. The service refuses the login and returns no access key.
- **Basis:** Seen in live response (the contract documents only the successful login)
- **Changes data:** No
- **Contract reference:** `POST /users/login`: documented responses 200
```

Data-driven variant, adding a **Variations** table:

```md
- **Request:** Send a valid invoice request, leaving out one required detail at a time.
- **Variations:**

  | Left out |
  |---|
  | street |
  | city |
  | … |

- **Expected response:** **422 Unprocessable Entity** for each, naming the missing detail.
```

## API test-plan template (`test-plans/<site>/api/test-plan.md`)

```md
# API test plan — <Site>

| | |
|---|---|
| API | <base URL> |
| Contract | <URL> (OpenAPI <version>), snapshot in api-context/<site>/ (<date>) |
| Related UI plan | ../test-plan.md (if any) |
| Status | Draft / Reviewed / Approved |
| Last updated | <date> |

## 1. Purpose
## 2. Scope — resources and operations in scope (table linking to case files), and what's out of scope with reasons
## 3. How we will test — contract-first; response shape checked on every success; data-driven validation; run order
## 4. Access and test data — how an access key is obtained (in words), token lifetime, accounts from environment settings, data created and cleaned up
## 5. When testing starts and when it's done
## 6. Risks and how we handle them
## 7. Coverage — per operation: which checklist scenarios are covered (✓ / n/a / deferred), and every documented status code covered
## 8. Test case summary — per file: cases, variations, High/Medium/Low, by basis; totals (counted from the files)
## 9. Contract findings and questions — numbered; each: what the contract says, what was seen or is missing, impact, case ID
## 10. Suggested order for automation (→ api-testing skill)
```

## Procedure

1. **Context:** reuse `api-context/<site>/INVENTORY.md`, or generate it (`npm run api:inventory`). Record the contract URL in the site's `ui-context/<site>/MAP.md` if it exists.
2. **Scope:** pick resources (see *Scope first*). Read the UI plan's backend checks and quirks for business rules worth testing.
3. **Cases:** for every operation in scope, walk the checklist. Write one file per resource. Use one live call only when a gap blocks an expected result, and label it **Seen in live response**.
4. **Plan:** fill the template. Build *Coverage* and *Summary* by **counting** from the files.
5. **Findings:** list contract problems (operations that change data without auth, undocumented error bodies, inline or missing schemas, statuses not honoured).
6. **Index:** add or refresh the site row in `test-plans/README.md`.
7. **Check:** no JSON/code outside the Endpoint field: `grep -nE '\{"|getBy|expect\(|Bearer|\.parse\(' test-plans/<site>/api/test-cases/*.md` should return nothing. Every case has Priority, Endpoint, Expected response, Basis, Changes data. Every documented status of every in-scope operation is covered or deliberately excluded.

## Relation to other skills

- **UI plan (`test-planning`):** its *Backend checks* file keeps only checks that support UI flows, and links here for full API coverage. Don't duplicate cases. Reference the API case ID instead.
- **Automation (`api-testing`):** each API case becomes a spec in `tests/api/<site>/<resource>.spec.ts`, with the case ID in a comment above the test. Variations become `for...of` loops. Expected responses become status + Zod schema assertions. When an automated case passes, a **Needs confirming** basis becomes **Seen in live response** (or "Confirmed by automated run on <date>").
